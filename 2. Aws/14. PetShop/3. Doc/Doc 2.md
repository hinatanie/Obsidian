## Problem 4: Allow the user to sign in to the AWS Console
An IAM user does not automatically receive a password.
Without console access, the user cannot sign in through a browser.
## Solution
Enable the option similar to:
```
Provide user access to the AWS Management Console
```
AWS may then ask how the user should be created.
Depending on the current interface, you may see a recommendation to manage human access through IAM Identity Center. Because you are intentionally creating an IAM user for this exercise, continue with the IAM-user option when AWS provides it.
For the console password, choose one of these:
```
Autogenerated password
```
or:
```
Custom password
```
For your own account, a custom strong password is easier to manage securely.
Example structure:
```
AuctionDev!2026-Strong
```
Do not copy that exact password.
AWS requires a console password for an IAM user that needs browser access.


### Problem 6: Give the user administrator permissions
Creating the user only creates an identity. It does not automatically grant permission to create EC2, RDS, S3, or IAM resources.
### Solution
On the permissions page, choose:
```
Add user to group
```
Then create a group, for example:
```
auction-admins
```
Attach this AWS-managed policy to the group:
```
AdministratorAccess
```
Then add `auction-dev-admin` to that group.  
The structure becomes:
```
auction-dev-admin
    ↓
Member of auction-admins
    ↓
Group has AdministratorAccess
    ↓
User can manage AWS development resources
```
Using a group is better than attaching the policy directly to the user because future administrators can be added to the same group without repeating the policy configuration.  
Be aware that `AdministratorAccess` is extremely powerful. Use it for your personal development administrator, not for your FastAPI application.

###### Problem 10: Enable MFA for `auction-dev-admin`

###### Problem 1: What does “Users must create a new password at next sign-in” mean?
Right now, **Autogenerated password** is selected.  
That means AWS will create the first password for `auction-dev-admin`.
###### Solution
Because AWS generated the password, it treats that password as temporary.  
With this checkbox selected:
```
Users must create a new password at next sign-in
```
the flow is:
```
AWS generates temporary password
    ↓
You sign in as auction-dev-admin
    ↓
AWS asks you to create your own new password
    ↓
The temporary password stops being used
```
AWS describes this option as requiring the generated password to be used only for the initial sign-in, after which the user must choose a new one.
###### What should you choose on your screen?
Because you currently selected:
```
Autogenerated password
```
keep this checkbox selected:
```
☑ Users must create a new password at next sign-in
```
This is the simplest and safest choice.  
After AWS creates the user:
1. Copy the autogenerated password.
2. Open an incognito browser window.
3. Sign in as `auction-dev-admin`.
4. Enter the autogenerated password.
5. AWS will ask you to create a new permanent password.
6. Save the new password in your password manager.

###### Problem 3: What is `IAMUserChangePassword`?
The text under the checkbox says AWS automatically gives the user the `IAMUserChangePassword` policy.  
Without permission, a new IAM user might not be allowed to change its own password.
###### Solution
When the checkbox is selected, AWS adds permission so that:
```
auction-dev-admin
    ↓
Can change its own password
    ↓
Cannot change other users’ passwords through this policy
```
This permission is needed because AWS will require the user to replace the temporary password at first sign-in. AWS documents that IAM users must be granted permission to change their own passwords.

###### Main Problem
AWS needs a way to make sure an IAM user **can never receive more permissions than a specified limit**, even when someone later attaches a powerful permission policy.  
The section in your screenshot is called a **permissions boundary**.
###### Problem 1: What is a permissions boundary?
###### Solution
A permissions boundary is a **maximum permission limit** for an IAM user.  
Think of it as a fence:
```
Permissions attached to the user
              ↓
Permissions boundary checks the maximum allowed
              ↓
Actual permissions the user receives
```
A boundary **does not give permissions by itself**. It only restricts permissions granted by other policies.
###### Example
Suppose the user receives this policy:
```
AdministratorAccess
```
That policy normally permits almost everything.  
But suppose the permissions boundary permits only:
```
EC2
S3
```
The user can use only EC2 and S3—not everything in `AdministratorAccess`.
```
Attached policy:        All AWS services
Boundary:               EC2 + S3 only
Actual permissions:     EC2 + S3 only
```
The action must be permitted by **both** the attached policy and the boundary.


###### Main Problem
AWS is telling you that **creating an IAM user does not automatically create credentials for programs**.  
You create the IAM user first. Later, you may create special credentials depending on how that user will access AWS.
###### Problem 1: What is programmatic access?
###### Solution
**Programmatic access** means accessing AWS through software rather than manually using the AWS website.  
Examples include:
```
AWS CLI commands
Python or Java applications
AWS SDKs
Automation scripts
Git connecting to AWS CodeCommit
```
For example:
```
aws s3 ls
```
This command needs credentials so AWS can determine:
```
Which IAM user is making the request?
Is that user allowed to list S3 buckets?
```


###### Problem 2: What are access keys?
###### Solution
Access keys are credentials commonly used by the AWS CLI, SDKs, and applications.  
They contain two parts:
```
Access key ID
Secret access key
```
They work somewhat like:
```
Access key ID     = username
Secret access key = password
```

###### Problem 3: What are service-specific credentials?
###### Solution
These are credentials that work with **only one particular AWS service**.  
For example:
```
AWS CodeCommit credentials → only for accessing CodeCommit Git repositories
Amazon Keyspaces credentials → only for connecting to Amazon Keyspaces
```
Unlike normal AWS access keys, service-specific credentials cannot generally be used across multiple AWS services.
