A Security Group is firewall for your EC2 instance

Security Groups only have allow rules and do not have deny rules
That means you cannot write
```
Deny SSH from this IP
```
If traffic does not match any allow rule, it is automatically blocked

---
Security Groups have two types of rules
Inbound rules control traffic coming into the EC2 instance
Inbound traffic is automatically denied by Security Groups unless you add inbound rule. That is why, after creating an EC2 instance, you often need to add an inbound rule for SSH, HTTP, or HTTPS 
```
HTTP  port 80  from 0.0.0.0/0
HTTPS port 443 from 0.0.0.0/0
SSH   port 22  from 0.0.0.0/0
```

Outbound rules control traffic going out from the EC2 instance
By default, AWS allows all outbound traffic but if you remove all outbound rules then the EC2 instance cannot send traffic out

---
Two EC2 instances can communicate only when their Security Group rules allow it
Example:
```
Backend EC2 want to communicate with Database EC2
```
A good rule would be:
```
Type:   PostgreSQL
Port:   5432
Source: Backend Security Group
```
This means only EC2 instances using the Backend Security Group can connect to the database. 
This is better than allowing all IP addresses

---
In a normal computer, you have a network card or Wi-Fi adapter to connect to the network.

In AWS, an EC2 instance has a virtual network card called an ENI( Elastic Network Interface )
**EC2 uses a network interface to send/receive traffic**
Security Group is firewall attached to that network card

A Security Group is actually attached to a network interface, not directly only to the EC2 machine itself.

The firewall controls traffic through the Wi-Fi adapter
So the firewall is not attached to the laptop directly
It is attached to the network card

When you go to AWS and change the Security Group of an EC2 instace, AWS actually changes the Security Group on that  EC2's network interface

AWS design it because one EC2 can have more than one network interface
Example:
```
EC2 Instance
   |
   |-- ENI 1 → Security Group A
   |   
   |-- ENI 2 → Security Group B
```
So different network interfaces on the same EC2 can have different Security Groups

---
A Security Group rule can allow traffic from different sources
**With CIDR**
```
SSH port 22 from 203.0.113.10/32
```
This allows one specific IP address
```
HTTP port 80 from 0.0.0.0/0
```
This allows everyone on the internet

**With another Security Group in the same VCP**
```
Database allows MySQL from Backend Security Group
```
This mean the database does not care about fixed IP addresses. It only allows instances that belong to the backend Security Group

**With Security Group in another peered VPC**
Normally, two VPC's are separate networks

By default, resources inside VPC A cannot talk privately to resources inside VPC B

But if you create VPC peering, you connect them privately
After peering, EC2 instances in VPC A can communicate with EC2 instances in VPC B using private IP addresses, not public internet

Example
```
VPC A
- Backend EC2
- Security Group: sg-backend
  
VPC B
- Database EC2
- Security Group: sg-backend
```
You want backend EC2 in VPC A connect to Database EC2 in VPC B
But you do not want to allow everyone
Bad rule:
```
Allow PostgreSQL port 5432 from 0.0.0.0/0
```
This means everyone can try to connect
Better rule:
```
sg-database inbound rule:
Type:   PostgreSQL
Port:   5432
Source: sg-backend
```
This means only EC2 instances that use sg-backend can connect to the database or only backend EC2 machines with that Security Group can connect to the database

Even though sg-backend is in another VPC, that backend also can connect to the database

It is useful because it is safer and easier than using IP addresses, without Security Group, you may need to write
```
Allow 10.0.1.25/32  
Allow 10.0.1.26/32  
Allow 10.0.1.27/32
```
If your backend EC2 IP changes, your rule may break
With Security Group, any EC2 using sg-backend can connect, even if its private IP changes

---
Example for an inbound rule:
```
Source:   sg-backend
Port:     5432
Protocol: TCP
```
This means allowing resources that is attach to Security Group sg-backend to connect to this database on port 5432

Example for an outbound rule:
```
Destination: 0.0.0.0/0
Port:        443
Protocol:    TCP
```
This means allowing this EC2 instance to connect to anywhere on HTTPS port 443

If backend EC2 wants to connect to database EC2
Backend outbound rule:
```
Destination: sg-database
Port: 5432
Protocol: TCP
```
Database inbound rule:
```
Source: sg-backend
Port: 5432
Protocol: TCP
```
---
**Standard Protocols and Ports**

A protocol is the communication method
A port identifies the service

|Service|Protocol|Port|
|---|---|---|
|SSH|TCP|22|
|HTTP|TCP|80|
|HTTPS|TCP|443|
|PostgreSQL|TCP|5432|
|MySQL|TCP|3306|
|Redis|TCP|6379|
SSH uses port 22
So if you want to SSH into an EC2 instance, the EC2 security group needs
```
Inbound rule:
Source: your IP address
Port: 22
Protocol: TCP
```
That means only your IP address can SSH into the EC2 instance
