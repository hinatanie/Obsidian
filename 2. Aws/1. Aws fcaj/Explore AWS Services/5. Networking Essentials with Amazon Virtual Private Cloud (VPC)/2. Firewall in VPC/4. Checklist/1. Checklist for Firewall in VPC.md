##### **What are security controls in `Amazon VPC`?**
`Amazon VPC` has security controls that work like firewalls.
They help you decide:
```text
Who can connect to my resources?
Where can my resources connect to?
Which traffic should be allowed or blocked?
```
The two main security controls are:
```text
Security Groups
NACLs
```
`Security Groups` usually protect `EC2` instances.
`NACLs` protect `subnets`.
##### **What is a `Firewall`?**
A `Firewall` is a system that allows or blocks network traffic based on rules.
Simple idea:
```text
Firewall = traffic guard
```
A firewall checks traffic and decides:
```text
Allow this traffic
Block this traffic
```
In `AWS`, common firewall-like controls are:
```text
Security Group
Network ACL / NACL
```
##### **What is a `Virtual Firewall`?**
A `Virtual Firewall` is a software-based firewall.
It filters network traffic without using physical hardware.
```text
Virtual Firewall = firewall in software
```
In `Amazon VPC`, both `Security Groups` and `NACLs` are virtual firewall controls.
They are not physical firewall boxes.
They are AWS networking security features.
##### **What is a `Security Group`?**
A `Security Group` is a virtual firewall for an `EC2` instance.
```text
Security Group = firewall for EC2 instance
```
A `Security Group` controls traffic at the `instance level`.
That means it is attached directly to an `EC2` instance, not directly to the whole `subnet`.
Each `EC2` instance can have different `Security Group` rules.
##### **What does `Instance Level` mean?**
`Instance level` means the rule is applied directly to an `EC2` instance.
```text
Instance level = applied to one EC2 instance
```
For example:
```text
EC2 A → Security Group A
EC2 B → Security Group B
EC2 C → Security Group C
```
Each `EC2` instance can have different inbound and outbound rules.
That is why `Security Groups` are called `instance-level` firewalls.
##### **What traffic does a `Security Group` control?**
A `Security Group` controls two directions of traffic:
```text
Inbound traffic
Outbound traffic
```
`Inbound traffic` means traffic coming into your `EC2` instance.
`Outbound traffic` means traffic going out from your `EC2` instance.
##### **What is `Inbound Traffic`?**
`Inbound traffic` means traffic coming into your `EC2` instance.
Example:
```text
Internet user → EC2 instance
```
If you want users to access your web server, you may allow:
```text
HTTP port 80
HTTPS port 443
```
If you want to connect to your server using `SSH`, you may allow:
```text
SSH port 22
```
Without inbound rules, people from the internet cannot connect to your `EC2` instance.
##### **What is `Outbound Traffic`?**
`Outbound traffic` means traffic going out from your `EC2` instance.
Example:
```text
EC2 instance → Internet
```
By default, `Security Groups` allow all outbound traffic.
So normally, your `EC2` instance can connect to external services unless you restrict outbound rules.
Example outbound activities:
```text
Download software updates
Call external APIs
Connect to package repositories
Send logs to external services
```
##### **What is the default outbound rule of a `Security Group`?**
By default, `Security Groups` allow all outbound traffic.
Example:
```text
Outbound rule:
Type:        All traffic
Protocol:    All
Port range:  All
Destination: 0.0.0.0/0
```
This means the `EC2` instance can send traffic to anywhere on the internet.
You can restrict outbound rules if your system needs stronger security.
##### **Why can nobody connect to a new `EC2` instance by default?**
After creating an `EC2` instance, people from the internet cannot connect to it unless you add inbound rules.
Example:
```text
No inbound rule for HTTP
→ Users cannot access web server on port 80
No inbound rule for HTTPS
→ Users cannot access web server on port 443
No inbound rule for SSH
→ You cannot SSH into the EC2 instance
```
This is safer because AWS does not expose your instance to the internet automatically.
##### ##### ##### **How to allow `HTTP` traffic to an `EC2` instance?**
To allow web traffic using `HTTP`, add this inbound rule to the `Security Group`:
```text
Inbound rule:
Type:   HTTP
Port:   80
Source: 0.0.0.0/0
```
This means anyone from the internet can access your `EC2` instance on port `80`.
`0.0.0.0/0` means all IPv4 addresses.
This is common for public web servers.
##### ##### ##### **How to allow `HTTPS` traffic to an `EC2` instance?**
To allow secure web traffic using `HTTPS`, add this inbound rule:
```text
Inbound rule:
Type:   HTTPS
Port:   443
Source: 0.0.0.0/0
```
This means anyone from the internet can access your `EC2` instance on port `443`.
`HTTPS` is usually used for secure websites with `SSL/TLS`.
##### ##### ##### **How to allow `SSH` access to an `EC2` instance?**
To allow `SSH`, add this inbound rule:
```text
Inbound rule:
Type:   SSH
Port:   22
Source: your-ip-address/32
```
This is safer than allowing everyone.
Avoid this for `SSH` if possible:
```text
Inbound rule:
Type:   SSH
Port:   22
Source: 0.0.0.0/0
```
This allows anyone on the internet to try connecting to your server using `SSH`.
For better security, use your own IP address:
```text
Source: 203.0.113.10/32
```
This means only that one IP address can attempt to connect by `SSH`.
##### **What does `0.0.0.0/0` mean in a `Security Group`?**
`0.0.0.0/0` means all IPv4 addresses.
Example:
```text
Source: 0.0.0.0/0
```
This means traffic can come from anywhere on the internet.
It is commonly used for public web traffic:
```text
HTTP  port 80  from 0.0.0.0/0
HTTPS port 443 from 0.0.0.0/0
```
But it is dangerous for sensitive ports like `SSH`.
##### **What does `Security Group` is `stateful` mean?**
`Security Groups` are `stateful`.
That means they remember who started the connection.
Example:
```text
EC2 → Internet
Internet → EC2 response
```
If the `EC2` instance starts a connection to the internet, the response traffic is automatically allowed back.
You do not need to manually create a matching inbound rule for the response.
##### **Why is `stateful` important?**
`Stateful` is important because it makes `Security Groups` easier to manage.
Example:
```text
Outbound:
EC2 → Ubuntu update server
Inbound response:
Ubuntu update server → EC2
```
Because the `Security Group` is `stateful`, the reply is automatically allowed.
You only need to focus on which new connections are allowed.
##### **What is a `NACL`?**
`NACL` means `Network Access Control List`.
A `NACL` is a firewall for a `subnet`.
```text
NACL = firewall for subnet
```
A `NACL` controls traffic entering and leaving a `subnet`.
It works at the `subnet level`.
##### **What does `Subnet Level` mean?**
`Subnet level` means the rule is applied to the whole `subnet`.
```text
Subnet level = applied to all resources inside a subnet
```
For example:
```text
Subnet A
├── EC2 1
├── EC2 2
└── EC2 3
```
If `Subnet A` uses one `NACL`, then all three `EC2` instances are affected by that `NACL`.
##### ##### ##### **How does a `NACL` affect resources in a subnet?**
If a `NACL` is attached to a `subnet`, it affects traffic going in and out of that `subnet`.
Example:
```text
Subnet A uses NACL A
EC2 1 inside Subnet A
EC2 2 inside Subnet A
EC2 3 inside Subnet A
```
All three `EC2` instances are affected by `NACL A`.
So if `NACL A` blocks traffic on port `80`, then resources in that subnet are affected by that rule.
##### **What does `NACLs are stateless` mean?**
`NACLs` are `stateless`.
That means they do not remember previous traffic.
With a `Security Group`, the response is automatically allowed because `Security Groups` are `stateful`.
But with a `NACL`, you need rules for both directions.
```text
Outbound traffic: EC2 → Internet
Inbound traffic:  Internet → EC2 response
```
If you allow only outbound traffic but block inbound response traffic, the connection may fail.
##### **Why do `NACLs` need inbound and outbound rules?**
`NACLs` need inbound and outbound rules because they are `stateless`.
Example:
```text
EC2 → Internet
Internet → EC2 response
```
For this to work with a `NACL`, you need both:
```text
Outbound rule:
Allow EC2 to send traffic out
Inbound rule:
Allow response traffic to come back
```
The `NACL` does not automatically remember that the `EC2` started the connection.
##### **What is the difference between `Security Group` and `NACL` state?**
`Security Groups` are `stateful`.
`NACLs` are `stateless`.
```text
Security Group:
Stateful
Response traffic is automatically allowed
NACL:
Stateless
Response traffic must be allowed by rules
```
Simple idea:
```text
Security Group remembers connections
NACL does not remember connections
```
##### ##### ##### **How are `NACL` rules checked?**
`NACL` rules are checked by rule number.
Lower numbers are checked first.
Example:
```text
Rule 100: Allow HTTP
Rule 200: Deny all traffic
```
AWS checks rule `100` first.
If traffic matches rule `100`, AWS applies that rule and stops checking later rules.
So rule order is very important.
##### **Why is `NACL` rule order important?**
`NACL` rule order is important because AWS checks lower rule numbers first.
Example:
```text
Rule 100: Deny HTTP
Rule 200: Allow HTTP
```
In this case, `HTTP` is denied because rule `100` is checked before rule `200`.
Even though rule `200` allows `HTTP`, it does not matter because the earlier matching rule already denied it.
##### **What is a good practice for `NACL` rule numbers?**
A good practice is:
```text
Use lower numbers for more specific rules
Use higher numbers for more general rules
```
Example:
```text
Rule 100: Allow HTTP from trusted IP range
Rule 200: Allow HTTPS from trusted IP range
Rule 300: Deny all other traffic
```
This makes the `NACL` easier to understand and safer to manage.
**Does every subnet need a `NACL`?**
Yes.
Each `subnet` must be connected to exactly one `NACL`.
```text
One subnet → One NACL
```
A `subnet` cannot have zero `NACLs`.
A `subnet` also cannot have more than one `NACL` at the same time.
**Can one `NACL` be used by many subnets?**
Yes.
One `NACL` can be associated with multiple `subnets`.
Example:
```text
NACL A
├── Public Subnet 1
├── Public Subnet 2
└── Public Subnet 3
```
But each `subnet` can only be associated with one `NACL` at a time.
Simple idea:
```text
One subnet can use only one NACL
One NACL can be used by many subnets
```
##### **What types of `NACLs` are there?**
`NACLs` can be:
```text
Default NACL
Custom NACL
```
The `Default NACL` is automatically created with your `VPC`.
A `Custom NACL` is created by you.
##### **What is a `Default NACL`?**
A `Default NACL` is the `NACL` automatically created with your `VPC`.
By default, it allows all inbound and outbound traffic.
```text
Default NACL:
Allow all inbound traffic
Allow all outbound traffic
```
This makes it easier for resources in the `VPC` to communicate when you first create the network.
##### **What is a `Custom NACL`?**
A `Custom NACL` is a `NACL` that you create yourself.
You need to be careful with a `Custom NACL`.
If you do not configure the rules correctly, it can block traffic.
Example problem:
```text
Inbound rule allows HTTP
Outbound rule does not allow response traffic
Result: connection may fail
```
Because `NACLs` are `stateless`, both inbound and outbound rules matter.
##### **Why should you be careful with `Custom NACLs`?**
You should be careful because `Custom NACLs` can block traffic if rules are missing or ordered incorrectly.
Common mistakes:
```text
Forgetting outbound response rules
Using wrong rule order
Denying traffic before allowing it
Forgetting ephemeral ports
Associating the wrong subnet
```
For many beginner projects, it is common to keep the `Default NACL` open and control access mainly with `Security Groups`.
Later, when you need stronger subnet-level security, you can add stricter `NACL` rules.
##### **What are `Ephemeral Ports`?**
`Ephemeral ports` are temporary ports used for return traffic.
When an `EC2` instance connects to an internet server, the response may come back to a temporary high-numbered port.
Example:
```text
EC2 → Web server port 443
Web server → EC2 ephemeral port
```
For `NACLs`, this matters because `NACLs` are `stateless`.
You may need to allow ephemeral port ranges for response traffic.
Example common range:
```text
1024-65535
```
This is one reason `NACLs` are more difficult to configure than `Security Groups`.
##### **What is the main difference between `Security Group` and `NACL`?**
A `Security Group` protects an `EC2` instance.
A `NACL` protects a `subnet`.
```text
Security Group = firewall for EC2 instance
NACL           = firewall for subnet
```
A `Security Group` works at the `instance level`.
A `NACL` works at the `subnet level`.
##### **What is the difference between `Security Group` and `NACL`?**
Here is the simple comparison:
```text
Security Group:
- Instance-level firewall
- Attached to EC2 instances
- Stateful
- Allows rules only
- Response traffic is automatically allowed
- Good for controlling access to specific instances
NACL:
- Subnet-level firewall
- Attached to subnets
- Stateless
- Supports allow and deny rules
- Response traffic must be allowed manually
- Good for broad subnet-level control
```
Use `Security Groups` for most normal access control.
Use `NACLs` when you need subnet-level allow or deny rules.
##### **What does `Protocol` mean?**
A `Protocol` is a communication rule used by network traffic.
Examples:
```text
TCP
UDP
ICMP
```
`TCP` is commonly used for web traffic, `SSH`, and many application connections.
`UDP` is commonly used for faster connectionless traffic.
`ICMP` is commonly used for tools like `ping`.
##### **What is a `Protocol Number`?**
A `Protocol Number` is a number that identifies a network protocol.
Examples:
```text
TCP  = 6
UDP  = 17
ICMP = 1
```
AWS security rules can use protocol names or protocol numbers.
For normal use, you usually select protocol names like `TCP`, `UDP`, or `ICMP`.
##### **What is `SSH`?**
`SSH` means `Secure Shell`.
`SSH` is a protocol used to securely connect to a server remotely.
Example:
```bash
ssh ubuntu@your-ec2-public-ip
```
This command connects to an `EC2` instance as the `ubuntu` user.
To make this work, the `Security Group` must allow inbound `SSH` traffic on port `22`.
##### **What is `Port 22`?**
`Port 22` is the standard port used by `SSH`.
Example `Security Group` rule:
```text
Inbound rule:
Type:   SSH
Port:   22
Source: your-ip-address/32
```
This allows your computer to connect to the `EC2` instance using `SSH`.
For security, do not open port `22` to everyone unless it is only for temporary testing.
##### **What is `HTTP` port `80`?**
`HTTP` uses port `80`.
Example `Security Group` rule:
```text
Inbound rule:
Type:   HTTP
Port:   80
Source: 0.0.0.0/0
```
This allows users from the internet to access your web server using `HTTP`.
For production websites, `HTTPS` is preferred.
##### **What is `HTTPS` port `443`?**
`HTTPS` uses port `443`.
Example `Security Group` rule:
```text
Inbound rule:
Type:   HTTPS
Port:   443
Source: 0.0.0.0/0
```
This allows users from the internet to access your website securely.
`HTTPS` encrypts traffic using `SSL/TLS`.
##### **What is `VPC Peering`?**
`VPC Peering` is a connection between two `VPCs`.
It allows resources in the two `VPCs` to communicate using private IP addresses.
Example:
```text
VPC A: 10.0.0.0/16
VPC B: 10.1.0.0/16
VPC A EC2 → VPC Peering → VPC B EC2
```
With `VPC Peering`, traffic does not need to go through the public internet.
The resources communicate using private networking.
##### **Why do we use both `Security Groups` and `NACLs`?**
We use both because they protect different layers.
```text
Security Group = protects EC2 instance
NACL           = protects subnet
```
This gives layered security.
Example:
```text
NACL:
Allow general web traffic into subnet
Security Group:
Allow only specific traffic into EC2
```
This is called defense in depth.
It means you have more than one layer of protection.
##### ##### ##### **How should you think about `Security Groups` and `NACLs` together?**
Think of `NACL` as the gate for the `subnet`.
Think of `Security Group` as the gate for the `EC2` instance.
```text
Internet
→ NACL checks subnet traffic
→ Security Group checks EC2 traffic
→ EC2 instance
```
For outbound traffic:
```text
EC2 instance
→ Security Group checks outbound traffic
→ NACL checks subnet outbound traffic
→ Internet
```
Both must allow the traffic for the connection to work.
##### **What is a simple example for a public web server?**
Suppose you have an `EC2` instance running a web server in a `public subnet`.
The `Security Group` may allow:
```text
Inbound rules:
HTTP   80  from 0.0.0.0/0
HTTPS 443 from 0.0.0.0/0
SSH    22  from your-ip-address/32
Outbound rules:
All traffic to 0.0.0.0/0
```
This allows users to access the website.
It also allows you to connect by `SSH` from your own IP address.
##### **What is a simple example for a private backend server?**
Suppose you have a backend `EC2` instance in a `private subnet`.
You may not allow direct internet access to it.
Example `Security Group` inbound rules:
```text
Inbound rules:
App port 8080 from Load Balancer Security Group
SSH port 22 from Bastion Host Security Group
```
This means users cannot directly connect to the backend server from the internet.
Only trusted AWS resources can connect to it.
##### **What is a simple example for a database server?**
Suppose you have a `MySQL` database in a `private subnet`.
You should not expose it to the internet.
Example `Security Group` inbound rule:
```text
Inbound rule:
Type:   MySQL/Aurora
Port:   3306
Source: Backend EC2 Security Group
```
This means only the backend server can connect to the database.
Internet users cannot connect directly to the database.
