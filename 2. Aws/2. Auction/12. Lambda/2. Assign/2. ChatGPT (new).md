# Main Problem
For this plan, API Gateway invokes dedicated Python Lambda handlers directly. The handlers reuse the existing domain rules, use cases, repositories, Pydantic schemas, and database models where practical, but they do not start FastAPI.

# Shared engineering rules
Every Lambda must follow these rules:
- The handler translates the AWS event, calls one application use case, and translates the result into a response.
- Domain rules must not be copied into handlers.
- HTTP responses must preserve the existing frontend contract unless an approved API change is recorded.
- JWT claims must be verified server-side; roles and user IDs must never be trusted from the request body.
- Database credentials must come from Secrets Manager, not source code.
- Database access must use RDS Proxy to protect MySQL from Lambda connection bursts.
- All mutation operations must use transactions.
- Retried events and repeated client requests must be idempotent.
- Logs must be structured and must not contain passwords, JWTs, secrets, or private image URLs.
- All timestamps must use UTC inside the backend.

# Risks

|Risk|Impact|Required mitigation|  
|Lambda opens too many MySQL connections|RDS exhaustion and failed bids|Use RDS Proxy, bounded concurrency, short transactions, and load tests|  
|Cold starts|Slower first request|Measure first; reduce package size and use provisioned concurrency only if required|  
|Concurrent bids|Incorrect winner|Row locks, transactional validation, idempotency keys, and concurrency tests|  
|Retried AWS events|Duplicate state|Idempotent consumers, unique event IDs, outbox records, and conditional updates|  
|WebSocket state stored in memory|Incorrect viewer count|Store connection state in DynamoDB and clean stale records|  
|API behavior changes during migration|Frontend failures|Contract inventory and automated compatibility tests|  
|Nine independent deployments drift|Operational errors|One versioned SAM template and environment configuration|  
|Long-running work exceeds Lambda limits|Timeout or partial work|Bound batch sizes, use SQS fan-out where needed, and monitor duration|
# Decisions Requiring Your Approval
1. **Direct Lambda handlers or FastAPI inside Lambda**
    - Recommendation: direct API Gateway Lambda handlers, because your stated goal is to replace FastAPI completely.
2. **Five domain HTTP Lambdas or one HTTP Lambda**
    - Recommendation: five domain Lambdas as defined in this document. They provide clearer ownership and independent scaling without creating one function per route.
3. **AWS SAM or Terraform**
    - Recommendation: AWS SAM for the first serverless migration.
4. **RDS Proxy**
    - Recommendation: required for this architecture before production cutover because multiple Lambdas can create connection bursts.
5. **JWT verification in shared Lambda code or an API Gateway authorizer**
    - Recommendation: begin with shared verification code to preserve current behavior; move to a Lambda authorizer later if central authorization becomes necessary.
6. **Viewer-count implementation**
    - Recommendation: query active DynamoDB connection records for version 1; introduce atomic counters only after measuring scale.
7. **Permanent chat history**
    - Recommendation: live chat only for version 1. Permanent history requires a separately approved persistence and moderation design.
8. **EC2 removal timing**
    - Recommendation: keep EC2 only as a rollback option during a short stability window; stop it only after LAM-016 passes and production stability is approved.
# Final Definition of Done
The migration is complete only when:
- Every required REST endpoint is invoked through API Gateway and direct Lambda handlers.
- No handler imports or starts FastAPI, Mangum, Uvicorn, or Gunicorn.
- WebSocket viewer count and chat use API Gateway, Lambda, and durable connection storage.
- Scheduled starts, scheduled endings, winner selection, image processing
- RDS access is safe under Lambda concurrency.
- Authentication, authorization, validation, status codes, and response formats pass contract tests.
- Retries cannot create duplicate bids, winners, images
- Logs, metrics, alarms, DLQ recovery, and rollback have been tested.
- The frontend has no production dependency on the EC2 backend.
- The user has approved final EC2 shutdown after the stability window.
