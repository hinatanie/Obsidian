For **LAM-003.10**, build one reusable adapter that reads a secret from AWS Secrets Manager, validates the JSON shape, and safely reuses it across warm Lambda invocations.
AWS recommends retrieving secrets with `GetSecretValue` and caching them when appropriate; the Lambda role needs `secretsmanager:GetSecretValue`. If the secret uses a customer-managed KMS key, the role may also need `kms:Decrypt`.
Create:
```
backend/app/shared/config/secrets.py
```
Use this:
```
import json
from dataclasses import dataclass
from functools import lru_cache
import boto3
from botocore.exceptions import BotoCoreError, ClientError
from app.shared.config.settings import get_settings
@dataclass(frozen=True)
class DatabaseSecret:
    username: str
    password: str
class SecretConfigurationError(RuntimeError):
    pass
def _get_secrets_client():
    settings = get_settings()
    return boto3.client(
        "secretsmanager",
        region_name=settings.aws_region,
    )
@lru_cache(maxsize=1)
def get_database_secret() -> DatabaseSecret:
    settings = get_settings()
    client = _get_secrets_client()
    try:
        response = client.get_secret_value(
            SecretId=settings.database_secret_arn
        )
    except (ClientError, BotoCoreError) as exc:
        raise SecretConfigurationError(
            "Unable to load database credentials."
        ) from exc
    secret_string = response.get("SecretString")
    if not secret_string:
        raise SecretConfigurationError(
            "Database secret does not contain SecretString."
        )
    try:
        secret_data = json.loads(secret_string)
    except json.JSONDecodeError as exc:
        raise SecretConfigurationError(
            "Database secret contains invalid JSON."
        ) from exc
    username = secret_data.get("username")
    password = secret_data.get("password")
    if not username:
        raise SecretConfigurationError(
            "Database secret is missing username."
        )
    if not password:
        raise SecretConfigurationError(
            "Database secret is missing password."
        )
    return DatabaseSecret(
        username=username,
        password=password,
    )
```
Your secret in AWS Secrets Manager should eventually contain JSON shaped roughly like:
```
{
  "username": "auction_app",
  "password": "REAL_SECRET_PASSWORD"
}
```
Do **not** put that JSON in source code. The code only knows the secret's ARN/name:
```
DATABASE_SECRET_ARN
        ↓
Secrets Manager
        ↓
SecretString
        ↓
username/password
```
The `@lru_cache(maxsize=1)` is intentional. On the first cold invocation:
```
Lambda starts
   ↓
Secrets Manager API call
   ↓
DatabaseSecret created
   ↓
cached
```
On a warm invocation:
```
same Lambda environment
   ↓
get_database_secret()
   ↓
reuse cached secret
```
This reduces repeated network calls. AWS also recommends client-side secret caching for performance and cost reasons.
For your first implementation, this simple process-level cache is enough. Later, if you enable automatic secret rotation, use AWS's Secrets Manager caching library or add an expiration strategy so a warm Lambda doesn't hold an old value indefinitely.
### Important: never log the secret
Wrong:
```
secret = get_database_secret()
print(secret)
print(secret.password)
```
Also wrong:
```
print(response["SecretString"])
```
If you need logs, log only safe information:
```
print(
    {
        "message": "Database secret loaded",
        "secretConfigured": True,
    }
)
```
Do not log passwords, secret JSON, JWT signing secrets, or complete connection strings.

### Unit-test it without calling real AWS
Do **not** make your unit tests depend on your real Secrets Manager account.
You can temporarily test the parsing behavior using mocking later. A simple pytest example:
```
from unittest.mock import Mock, patch
from app.shared.config.secrets import get_database_secret
@patch("app.shared.config.secrets._get_secrets_client")
def test_get_database_secret(mock_client_factory):
    mock_client = Mock()
    mock_client.get_secret_value.return_value = {
        "SecretString": (
            '{"username":"auction_user","password":"test-password"}'
        )
    }
    mock_client_factory.return_value = mock_client
    get_database_secret.cache_clear()
    secret = get_database_secret()
    assert secret.username == "auction_user"
    assert secret.password == "test-password"
```
You should also test these cases:
```
valid JSON                    → success
missing username              → controlled error
missing password              → controlled error
invalid JSON                  → controlled error
missing SecretString          → controlled error
AWS AccessDenied              → controlled error
```
### IAM permission
Your Lambda execution role needs access to this secret.
Conceptually, the IAM policy should allow:
```
{
  "Effect": "Allow",
  "Action": "secretsmanager:GetSecretValue",
  "Resource": "<your-secret-arn>"
}
```
Use the specific secret ARN rather than:
```
*
```
when practical. AWS recommends least-privilege permissions for Secrets Manager.
Do **not** do this:
```
boto3.client(
    "secretsmanager",
    aws_access_key_id="...",
    aws_secret_access_key="..."
)
```
Lambda should obtain temporary AWS credentials automatically from its execution IAM role.
### JWT secret
Your task mentions database/JWT secret configuration. You have two reasonable choices later:
```
Secret A:
auction/database
Secret B:
auction/jwt
```
or one structured secret containing multiple values.
I recommend keeping them separate because database credentials and JWT signing keys have different purposes and may eventually have different permissions/rotation schedules.
For now, finish the **database secret adapter first**. Then you can reuse the same generic retrieval mechanism for a JWT secret.
