### LAM-003.1 — Create shared package structure
Create roughly:
```
app/shared/
├── http/
│   ├── __init__.py
│   ├── request.py
│   ├── response.py
│   ├── cors.py
│   ├── context.py
│   ├── errors.py
│   └── validation.py
├── auth/
│   ├── __init__.py
│   ├── jwt.py
│   └── authorization.py
├── config/
│   ├── __init__.py
│   ├── settings.py
│   └── secrets.py
└── database/
    ├── __init__.py
    ├── session.py
    └── transaction.py
```
Done when all modules import successfully.
### LAM-003.2 — Standard JSON response helper
Create one reusable function for HTTP responses.
It should handle:
```
status code
JSON serialization
Content-Type
CORS headers
request ID
```
Target idea:
```
json_response(
    status_code=200,
    data={...},
    request_id="..."
)
```
All HTTP Lambdas should eventually use this instead of manually returning:
```
{
    "statusCode": 200,
    "body": ...
}
```
Acceptance check: all responses have the same format.
### LAM-003.3 — Shared CORS helper
Create one place defining your allowed origins and headers.
Support at least:
```
development frontend
production frontend
OPTIONS/preflight response
```
Do not duplicate CORS dictionaries in each Lambda.
Acceptance check: changing allowed origins requires changing one shared module only.
### LAM-003.4 — Request ID/context helper
Create a helper that obtains the API Gateway request ID if available.
Fallback to a generated UUID when needed.
The request ID should be reusable for:
```
logging
responses
error tracing
```
Acceptance check: every request can be correlated through one request ID.
### LAM-003.5 — API Gateway event parsing
Create an adapter for fields such as:
```
HTTP method
path
path parameters
query parameters
headers
body
request context
```
The rest of your application should not need to understand the raw AWS event structure.
Conceptually:
```
API Gateway event
       ↓
shared request adapter
       ↓
clean request object
       ↓
Lambda routing/use case
```
### LAM-003.6 — Safe JSON body parsing
Handle:
```
empty body
valid JSON
invalid JSON
Base64-encoded body if applicable
```
Invalid JSON must return a controlled client error rather than a Python traceback.
Acceptance check:
```
malformed JSON → controlled response
```
### LAM-003.7 — Shared errors and HTTP error mapping
Define shared exceptions or mappings for cases such as:
```
400 bad request
401 unauthenticated
403 forbidden
404 not found
409 conflict
422 validation failure
500 internal error
```
Your handlers should not each contain long `try/except` blocks translating the same errors.
Acceptance check: one error mapper controls HTTP behavior.
### LAM-003.8 — Reusable Pydantic validation
Create a shared helper for validating request payloads against Pydantic models.
It should convert Pydantic errors into your agreed HTTP error format.
For example:
```
JSON body
   ↓
Pydantic model
   ↓
valid object
```
or:
```
JSON body
   ↓
validation fails
   ↓
422 controlled response
```
Acceptance check: validation errors never escape as raw exceptions.
### LAM-003.9 — Environment configuration
Create shared settings for things like:
```
APP_ENV
AWS_REGION
DATABASE_SECRET_ARN
RDS_PROXY_HOST
DB_NAME
JWT algorithm
JWT expiration settings
```
Do not put real passwords or secret values here.
Acceptance check: configuration comes from environment variables rather than hardcoded production values.
### LAM-003.10 — Secrets Manager adapter
Create reusable code that retrieves the database/JWT secret configuration from AWS Secrets Manager.
Important responsibilities:
```
load secret by ARN/name
parse JSON secret
handle missing fields
avoid logging secret values
optionally cache safely across warm invocations
```
The Lambda should use an IAM role to access Secrets Manager.
Do not put AWS access keys in Python.
### LAM-003.11 — JWT verification
Create shared JWT verification code.
Validate at minimum:
```
signature
algorithm
expiration
required claims
subject/user ID
```
Do not trust:
```
user ID from request body
role from request body
email from request body
```
Authentication identity must come from verified JWT claims.
### LAM-003.12 — Reusable current-user authentication
Create a helper that:
```
reads Authorization header
requires Bearer token
verifies JWT
loads/resolves authenticated identity
returns current user/auth context
```
Expected failure examples:
```
missing token → 401
bad token → 401
expired token → 401
```
### LAM-003.13 — ACTIVE user authorization
Create a reusable guard/check such as conceptually:
```
require_active_user(...)
```
It must reject banned/inactive users according to your existing contract.
Expected:
```
authenticated ACTIVE user → allowed
authenticated BANNED user → 403
```
### LAM-003.14 — ADMIN authorization
Create reusable authorization for admin-only operations.
Conceptually:
```
require_admin(...)
```
It should require:
```
valid JWT
ACTIVE user
ADMIN role
```
A normal USER should receive `403`.
This will later be reused by `auction-admin-api`.
### LAM-003.15 — SQLAlchemy engine for RDS Proxy
Create database engine configuration that points to:
```
Lambda
  ↓
RDS Proxy
  ↓
MySQL
```
Not:
```
Lambda
  ↓
direct uncontrolled connections
  ↓
RDS
```
Configure the SQLAlchemy engine once at module scope where appropriate so warm Lambda invocations can reuse the engine/pool safely.
Do not open a transaction globally.
### LAM-003.16 — Database session factory
Create a reusable function for obtaining a SQLAlchemy session.
Conceptually:
```
session = create_session()
```
or an async equivalent depending on your existing SQLAlchemy architecture.
Responsibilities:
```
create session
use RDS Proxy engine
close correctly
never expose stale session state
```
### LAM-003.17 — Transaction helper
Create one reusable transaction boundary.
Expected behavior:
```
use case succeeds
    ↓
commit
    ↓
close
```
Failure:
```
use case raises
    ↓
rollback
    ↓
close
    ↓
re-raise/map error
```
This is especially important later for:
```
register
create session
start session
create item
place bid
create admin
```
### LAM-003.18 — Warm Lambda safety
This is a critical Lambda-specific task.
Remember:
```
cold invocation
      ↓
Python process stays alive
      ↓
second invocation may reuse it
```
Reusable:
```
SQLAlchemy engine
Secrets Manager client
configuration
```
Should **not** be reused across requests:
```
active transaction
request-scoped session
current user
request ID
request body
```
Acceptance test:
```
Invocation 1 fails during transaction
Invocation 2 succeeds normally
```
Invocation 2 must not inherit the previous rollback/transaction/user state.
### LAM-003.19 — Shared HTTP Lambda execution wrapper
Once the pieces above exist, create a common wrapper/controller flow.
Conceptually:
```
raw API Gateway event
        ↓
request context
        ↓
parse request
        ↓
authenticate if required
        ↓
validate request
        ↓
call use case
        ↓
standard response
```
And failures:
```
exception
   ↓
shared error mapper
   ↓
standard JSON error response
```
This greatly reduces handler duplication.

### LAM-003.23 — Transaction tests
Mock or use an isolated test database/session.
Verify:
```

```
Also test that a failed commit is handled safely.
### LAM-003.24 — Warm invocation tests
Simulate two sequential invocations inside the same Python process.
Example scenario:
```
Invocation A
→ opens transaction
→ throws exception
→ rollback + close
Invocation B
→ opens new session
→ succeeds
→ commit + close
```
Verify B is unaffected by A.
Also verify request ID/current-user state does not leak between invocations.
### LAM-003.25 — Final duplication check
Inspect:
```
lambdas/auth_api
lambdas/session_api
lambdas/item_api
lambdas/bid_api
lambdas/admin_api
```

```

Bearer parsing
CORS headers
JSON parsing
Pydantic error conversion
Secrets Manager reading
database session lifecycle
transaction commit/rollback
standard response format
```
Instead:
```
Lambda handlers
      ↓
app/shared/*
```
