# UC01 - Register User
## Actor
```
Guest
```
## Goal
Create a new account.
## Page
```
/register
```
## API
```
POST /api/v1/auth/register
```
## Request body
```
{
  "email": "seller@gmail.com",
  "password": "123456",
  "fullName": "Nguyen Van A",
  "phone": "0909123456"
}
```
## Backend flow
```
1. Guest submits register form.
2. FastAPI receives POST /api/v1/auth/register.
3. Validate request body.
4. Check if email already exists.
5. If email exists, return 400 EMAIL_ALREADY_EXISTS.
6. Hash password using bcrypt.
7. Create new user:
   - role = USER
   - status = ACTIVE
8. Save user to database.
9. Return user information.
```
## Success response
```
{
  "status": 201,
  "code": 1000,
  "message": "Register successfully",
  "data": {
    "id": "user-uuid",
    "email": "seller@gmail.com",
    "fullName": "Nguyen Van A",
    "phone": "0909123456",
    "role": "USER",
    "status": "ACTIVE"
  }
}
```
## FastAPI files
```
auth_router.py
auth_service.py
auth_schema.py
user_model.py
user_repository.py
```

```

```
## Request body

```
}
```
## Backend flow
```
1. User submits login form.
2. FastAPI receives POST /api/v1/auth/login.
```

# UC03 - Create Auction Session
#### Actor
```text
Logged-in Seller
```
#### Goal
The seller creates a new auction event that can later contain rules and auction items.
Examples:
```text
Luxury Watch Auction July 2026
Phone Auction July 2026
Laptop Auction Weekend
```
A newly created auction session starts as `DRAFT` because the seller is still preparing it.
The seller can add items, edit information, and configure rules before publishing the session.
#### API
```http
POST /api/v1/auction-sessions
```
#### Headers
```http
Authorization: Bearer <accessToken>
Content-Type: application/json
```
#### Request Body
```json
{
  "title": "Phone Auction July 2026",
  "description": "Auction session for phones including iPhone, Samsung, and Xiaomi.",
  "startTime": "2026-07-20T09:00:00",
  "endTime": "2026-07-20T18:00:00",
  "minIncrement": 50000
}
```
#### Validation Rules
```text
1. The access token must be valid.
2. title is required.
3. startTime is required.
4. endTime is required.
5. startTime must be before endTime.
6. minIncrement must be greater than 0.
```
#### Backend Flow
```text
1. Seller opens the Create Auction Session page.
2. Seller enters:
   - title
   - description
   - startTime
   - endTime
   - minIncrement
3. Frontend calls:
   POST /api/v1/auction-sessions
4. Backend validates the Bearer access token.
5. Backend gets sellerId from the JWT sub claim.
   The frontend must not send sellerId in the request body.
6. Backend validates the request body.
7. Backend checks:
   - startTime < endTime
   - minIncrement > 0
8. Backend begins one database transaction.
9. Backend creates the auction session:
   - seller_id = current authenticated user id
   - title = request.title
   - description = request.description
   - start_time = request.startTime
   - end_time = request.endTime
   - status = DRAFT
10. Backend flushes the auction session insert to obtain the generated session id.
11. Backend creates the auction session rule:
    - session_id = created session id
    - min_increment = request.minIncrement
12. If both records are created successfully:
    - commit the transaction
13. If either operation fails:
    - roll back the complete transaction
14. Backend returns the created auction session with HTTP 201.
```
#### Why the Initial Status Is `DRAFT`
The auction session is not ready for bidders immediately after creation.
The seller may still need to:
```text
Add auction items
Upload item images
Edit item information
Configure additional rules
Review the auction session
Publish the auction session
```
The recommended lifecycle is:
```text
DRAFT
  ↓ Seller finishes configuration and publishes
SCHEDULED
  ↓ Start time is reached
ACTIVE
  ↓ End time is reached
COMPLETED
```
#### Success Response
```json
{
  "status": 201,
  "code": 1000,
  "message": "Create auction session successfully",
  "data": {
    "id": "session-uuid",
    "sellerId": "seller-uuid",
    "title": "Phone Auction July 2026",
    "description": "Auction session for phones including iPhone, Samsung, and Xiaomi.",
    "startTime": "2026-07-20T09:00:00",
    "endTime": "2026-07-20T18:00:00",
    "status": "DRAFT",
    "rule": {
      "minIncrement": 50000
    }
  }
}
```
#### Possible Error Responses
##### Invalid or Missing Access Token
```http
401 Unauthorized
```
##### Invalid Auction Time
```http
400 Bad Request
```
```json
{
  "status": 400,
  "code": "INVALID_AUCTION_TIME",
  "message": "Start time must be before end time",
  "data": null
}
```
##### Invalid Minimum Increment
```http
400 Bad Request
```
```json
{
  "status": 400,
  "code": "INVALID_MIN_INCREMENT",
  "message": "Minimum increment must be greater than zero",
  "data": null
}
```

# UC06 - Create Auction Item
#### Actor
```text
Logged-in Seller
```
#### Goal
The seller adds an auction item to an auction session that they own.
Examples:
```text
iPhone 14 Pro Max 256GB
Samsung Galaxy S25 Ultra
MacBook Pro M4
Rolex Submariner
```
#### Page
```text
/seller/auction-sessions/:sessionId/items/create
```
#### API
```http
POST /api/v1/auction-sessions/{sessionId}/items
```
Example:
```http
POST /api/v1/auction-sessions/4381bbad-04ac-4088-b0b4-85fca226ef68d/items
```
The `sessionId` must use the standard UUID format.
Correct:
```text
4381bbad-04ac-4088-b0b4-85fca226ef68d
```
Incorrect:
```text
0x4381BBAD04AC4088B0B485CA226EF68D
```
#### Headers
```http
Authorization: Bearer <accessToken>
Content-Type: application/json
```
#### Request Body
```json
{
  "categoryId": "category-uuid",
  "title": "iPhone 14 Pro Max 256GB",
  "description": "Máy màu tím, dung lượng 256GB, pin 89%, ngoại hình đẹp, có trầy nhẹ ở viền. Bao gồm hộp và cáp sạc.",
  "startingPrice": 10000000
}
```
The frontend does not send these backend-controlled fields:
```text
sellerId
sessionId
currentPrice
status
```
#### Validation Rules
```text
1. The access token must be valid.
2. sessionId must be a valid UUID.
3. The auction session must exist.
4. The current seller must own the auction session.
5. The auction session must be in DRAFT status.
6. categoryId must reference an existing category when provided.
7. title is required.
8. startingPrice must be greater than 0.
```
#### Backend Flow
```text
1. Seller opens the Create Auction Item page.
2. Seller enters:
   - category
   - title
   - description
   - startingPrice
3. Frontend calls:
   POST /api/v1/auction-sessions/{sessionId}/items
4. Backend validates the Bearer access token.
5. Backend gets sellerId from the JWT sub claim.
6. Backend reads sessionId from the URL path.
7. Backend validates the request body.
8. Backend loads the auction session by sessionId.
9. If the session does not exist:
   - return 404 SESSION_NOT_FOUND
10. Backend compares:
    - auction_session.seller_id
    - current authenticated seller id
11. If the current seller does not own the session:
    - return 403 FORBIDDEN
12. Backend checks the auction session status.
13. The seller can only add items while the session is DRAFT.
14. If the session is not DRAFT:
    - return 400 SESSION_NOT_DRAFT
15. If categoryId is provided:
    - load the category
    - verify that the category exists
16. If the category does not exist:
    - return 404 CATEGORY_NOT_FOUND
17. Backend checks:
    - startingPrice > 0
18. Backend creates the auction item:
    - seller_id = current authenticated user id
    - session_id = sessionId
    - category_id = request.categoryId
    - title = request.title
    - description = request.description
    - starting_price = request.startingPrice
    - current_price = request.startingPrice
    - status = DRAFT
19. Backend saves the item.
20. Backend returns the created item with HTTP 201.
```
#### Why the Session Must Be `DRAFT`
The seller should only change the contents of an auction while it is still being prepared.
Once the session is published as `SCHEDULED`, bidders should be able to trust that its items and rules are finalized.
Recommended behavior:
```text
Session status = DRAFT
    → Add, edit, or delete items
Session status = SCHEDULED
    → Auction is published
    → Items should no longer be freely changed
Session status = ACTIVE
    → Bidding is taking place
    → Items cannot be added
Session status = COMPLETED
    → Auction has ended
    → Items cannot be added
```
#### Why the Initial Item Status Is `DRAFT`
`UNSOLD` should not be used when an item is first created.
`UNSOLD` normally means:
```text
The auction for this item has ended without a winner.
```
At creation time, the item has not entered the auction yet.
The recommended lifecycle is:
```text
DRAFT
  ↓ Item information and images are complete
READY
  ↓ Bidding begins
OPEN
  ↓ Auction closes with a winner
SOLD
```
Or:
```text
OPEN
  ↓ Auction closes without a valid winner
UNSOLD
```
An item may also become:
```text
CANCELLED
```
when it is removed before completion.
#### Why `currentPrice` Equals `startingPrice`
No bid exists when the item is first created.
Therefore:
```text
currentPrice = startingPrice
```
Example:
```text
startingPrice = 10,000,000 VND
currentPrice  = 10,000,000 VND
```
After the first valid bid:
```text
currentPrice = first accepted bid amount
```
#### Success Response
```json
{
  "status": 201,
  "code": 1000,
  "message": "Create auction item successfully",
  "data": {
    "id": "item-uuid",
    "sessionId": "session-uuid",
    "sellerId": "seller-uuid",
    "categoryId": "category-uuid",
    "title": "iPhone 14 Pro Max 256GB",
    "description": "Máy màu tím, dung lượng 256GB, pin 89%, ngoại hình đẹp, có trầy nhẹ ở viền. Bao gồm hộp và cáp sạc.",
    "startingPrice": 10000000,
    "currentPrice": 10000000,
    "status": "DRAFT"
  }
}
```

### Combined UC03 and UC06 Flow
```text
1. Seller logs in.
        ↓
2. Seller creates an auction session.
        ↓
3. Backend creates the session with DRAFT status.
        ↓
4. Backend creates the initial auction rule.
        ↓
5. Seller adds one or more auction items.
        ↓
6. Each item starts with DRAFT status.
        ↓
7. Seller completes item information and images.
        ↓
8. Items become READY.
        ↓
9. Seller publishes the auction session.
        ↓
10. Session becomes SCHEDULED.
        ↓
11. At startTime, session becomes ACTIVE.
        ↓
12. Items open for bidding.
        ↓
13. At endTime, each item becomes SOLD or UNSOLD.
        ↓
14. Session becomes COMPLETED.
```

# UC09 - Place Bid
## Actor
```
Logged-in User except the seller of the auction session
```
## Goal
Bid on an auction item.
## API
```
POST /api/v1/auction-items/{itemId}/bids
```
## Headers
```
Authorization: Bearer <accessToken>
Content-Type: application/json
```
## Request body
```
{
  "amount": 13000000
}
```
## Backend flow
```
1. Bidder opens auction item detail page.
2. Bidder enters bid amount.
3. Frontend calls POST /api/v1/auction-items/{itemId}/bids.
4. Backend gets bidderId from JWT.
5. Backend starts database transaction.
6. Backend locks auction item row using SELECT FOR UPDATE.
7. Backend checks item exists.
8. Backend checks auction session exists.
9. Backend checks session status is ACTIVE.
10. Backend checks current time is between session.start_time and session.end_time.
11. Backend checks bidder is not the seller.
12. Backend gets session rule.
13. Backend calculates minimum valid bid:
    - minimumBid = item.current_price + rule.min_increment
14. If request.amount < minimumBid, return 400 BID_TOO_LOW.
15. Backend updates old WINNING bid to OUTBID.
16. Backend creates new bid:
    - item_id = itemId
    - session_id = item.session_id
    - bidder_id = current user id
    - amount = request.amount
    - status = WINNING
17. Backend updates auction_items.current_price = request.amount.
18. Commit transaction.
19. Return new bid.
```
## Success response
```
{
  "status": 201,
  "code": 1000,
  "message": "Place bid successfully",
  "data": {
    "id": "bid-uuid",
    "itemId": "item-uuid",
    "sessionId": "session-uuid",
    "bidder" : {
        "bidderId": "bidder-uuid",
	    "bidderName": "Tran Van B",
    },
    "amount": 13000000,
    "status": "WINNING",
    "createdAt": "2026-07-20T10:30:00"
  }
}
```
## Very important for FastAPI
For bidding, you should use database transaction and row lock:
```
SELECT * FROM auction_items WHERE id = :item_id FOR UPDATE
```
Because if two users bid at the same time, you must prevent wrong `current_price`.

## Database Design
The project currently uses UUID values stored as `BINARY(16)` in MySQL.
Therefore, the category table should follow the same design instead of using `CHAR(16)`.
```sql
CREATE TABLE categories (
    id BINARY(16) PRIMARY KEY,
    name VARCHAR(150) NOT NULL,
    slug VARCHAR(150) NOT NULL UNIQUE,
    status ENUM(
        'ACTIVE',
        'INACTIVE'
    ) NOT NULL DEFAULT 'ACTIVE',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP,
    CONSTRAINT uq_categories_name UNIQUE (name)
);
```
Recommended indexes:
```sql
CREATE UNIQUE INDEX uq_categories_name
ON categories(name);
CREATE UNIQUE INDEX uq_categories_slug
ON categories(slug);
CREATE INDEX ix_categories_status
ON categories(status);
```
Because `name` and `slug` are already unique, MySQL automatically creates indexes for their unique constraints. You do not need to create duplicate indexes manually if the constraints already exist.

```text
1. Admin opens the User Management page.

   GET /api/v1/admin/users

4. Backend loads the current authenticated user.
5. Backend checks:

   - Current user role is ADMIN.
6. If the current user is not authenticated:
   - Return 401 UNAUTHORIZED.
7. If the current user is banned:
   - Return 403 USER_BANNED.
8. If the current user is not an admin:
   - Return 403 ADMIN_ACCESS_REQUIRED.
9. Backend validates query parameters:
   - page must be greater than or equal to 1.
   - pageSize must be between 1 and 100.
   - role must be ADMIN or USER.
   - status must be ACTIVE or BANNED.
   - sortBy must be createdAt, email, or fullName.
   - sortOrder must be asc or desc.
10. Backend creates a user query.
11. If keyword is provided, backend searches case-insensitively by:
    - email
    - full_name
    - phone
12. If role is provided, backend filters by role.
13. If status is provided, backend filters by status.
14. Backend counts the total number of matching users.
15. Backend applies sorting.
16. Backend applies pagination.
17. Backend returns the user list.
18. The response must never include password_hash.
```

##### Search Logic
When `keyword` is provided, backend searches using:
```sql
LOWER(email) LIKE LOWER('%keyword%')
OR LOWER(full_name) LIKE LOWER('%keyword%')
OR phone LIKE '%keyword%'
```
Example SQL logic:
```sql
SELECT
    id,
    email,
    full_name,
    phone,
    role,
    status,
    created_at,
    updated_at
FROM users
WHERE
    LOWER(email) LIKE LOWER('%nguyen%')
    OR LOWER(full_name) LIKE LOWER('%nguyen%')
    OR phone LIKE '%nguyen%'
ORDER BY created_at DESC
LIMIT 20 OFFSET 0;
```

---
##### Pagination Logic
```text
offset = (page - 1) × pageSize
```
Example:
```text
page = 3
pageSize = 20
offset = (3 - 1) × 20
offset = 40
```
SQL:
```sql
LIMIT 20 OFFSET 40
```

#### Repository Logic
```python
from sqlalchemy import func, or_, select
from sqlalchemy.ext.asyncio import AsyncSession
from app.models.user import User
SORT_COLUMN_MAPPING = {
    UserSortBy.CREATED_AT: User.created_at,
    UserSortBy.EMAIL: User.email,
    UserSortBy.FULL_NAME: User.full_name,
}
class UserRepository:
    def __init__(self, session: AsyncSession):
        self.session = session
    async def find_all(
        self,
        *,
        page: int,
        page_size: int,
        keyword: str | None,
        role: UserRole | None,
        status: UserStatus | None,
        sort_by: UserSortBy,
        sort_order: SortOrder,
    ) -> tuple[list[User], int]:
        conditions = []
        if keyword:
            normalized_keyword = f"%{keyword.strip().lower()}%"
            conditions.append(
                or_(
                    func.lower(User.email).like(normalized_keyword),
                    func.lower(User.full_name).like(normalized_keyword),
                    User.phone.like(f"%{keyword.strip()}%"),
                )
            )
        if role:
            conditions.append(User.role == role)
        if status:
            conditions.append(User.status == status)
        count_query = select(func.count(User.id))
        if conditions:
            count_query = count_query.where(*conditions)
        total_items = await self.session.scalar(count_query)
        total_items = total_items or 0
        sort_column = SORT_COLUMN_MAPPING[sort_by]
        if sort_order == SortOrder.ASC:
            order_expression = sort_column.asc()
        else:
            order_expression = sort_column.desc()
        offset = (page - 1) * page_size
        query = (
            select(User)
            .where(*conditions)
            .order_by(order_expression, User.id.asc())
            .offset(offset)
            .limit(page_size)
        )
        result = await self.session.execute(query)
        users = list(result.scalars().all())
        return users, total_items
```
The additional:
```python
User.id.asc()
```
acts as a stable secondary sort when multiple users have the same creation time, email ordering position, or full name.

#### Service Logic
```python
import math
class UserService:
    def __init__(self, user_repository: UserRepository):
        self.user_repository = user_repository
    async def get_user_list(
        self,
        *,
        page: int,
        page_size: int,
        keyword: str | None,
        role: UserRole | None,
        status: UserStatus | None,
        sort_by: UserSortBy,
        sort_order: SortOrder,
    ) -> UserListData:
        users, total_items = await self.user_repository.find_all(
            page=page,
            page_size=page_size,
            keyword=keyword,
            role=role,
            status=status,
            sort_by=sort_by,
            sort_order=sort_order,
        )
        total_pages = (
            math.ceil(total_items / page_size)
            if total_items > 0
            else 0
        )
        return UserListData(
            items=[
                UserListItem.model_validate(user)
                for user in users
            ],
            pagination=PaginationData(
                page=page,
                pageSize=page_size,
                totalItems=total_items,
                totalPages=total_pages,
                hasNextPage=page < total_pages,
                hasPreviousPage=page > 1,
            ),
        )
```

#### Security Rules
```text
1. Never return password_hash.
2. Only ACTIVE administrators may access the endpoint.
3. Do not allow pageSize greater than 100.
4. Do not pass sortBy directly into raw SQL.
5. Map allowed sort values to known database columns.
6. Use SQLAlchemy parameters instead of constructing raw SQL strings.
7. Treat an empty result as a successful response.
8. Search should be case-insensitive for email and full name.
9. Keep pagination and filtering on the database side.
10. Do not load every user and paginate in Python.
```

```text
1. An ACTIVE admin can view the user list.

5. The result supports pagination.
6. The result supports keyword search.
7. The result supports filtering by role.
8. The result supports filtering by status.
9. The result supports sorting.
10. The response never includes password_hash.
```

# Clean FastAPI layer responsibility
## Router layer
```
Receive HTTP request
Validate request body
Get current user if needed
Call service
Return response
```
Example:
```
bid_router.py
```
Should only handle:
```
POST /auction-items/{itemId}/bids
```
Do not put business logic in router.

---
## Service layer
```
Handle business logic
Check permissions
Check status
Check bid amount
Start database transaction
Call repository
```
Example:
```
bid_service.py
```
Handles:
```
- item exists or not
- session ACTIVE or not
- bidder cannot bid own item
- amount must be valid
- old WINNING bid becomes OUTBID
- new bid becomes WINNING
- update current_price
```

---
## Repository layer
```
Only database query
No business logic
```
Example:
```
bid_repository.py
```
Handles:
```
find winning bid
create bid
update bid status
find bids by bidder
```

# My recommendation for your app
For your current auction app, FastAPI is okay and clean.
But because this is a **realtime auction app**, remember this:
```
FastAPI REST API is good for:
- register
- login
- create session
- create item
- place bid
- view history
WebSocket is needed for:
- realtime current price update
- realtime bid notification
- online green status
- auction countdown update
```
So your backend should be:
```
FastAPI REST API + FastAPI WebSocket
```
Not REST only.
Best simple architecture:
```
React frontend
        ↓
FastAPI REST API
        ↓
MySQL database
React frontend
        ↓
FastAPI WebSocket
        ↓
Realtime bid updates
```
For your use case, this is a good clean structure.
