# Pet Shop AWS — Document 3: RDS, Spring Boot, React, and Operations
# Main Problem
The Pet Shop application needs a private MySQL database, a continuously running Spring Boot backend, a secure public API, and a React production deployment.
This document depends on completion of:
```
Document 1: Cost Control
Document 2: VPC and Network Foundation
```
Target request path:
```
User
 ├── React → CloudFront → Private S3 frontend bucket
 └── API HTTPS → Nginx on EC2 → 127.0.0.1:8080 → Spring Boot → Private RDS
```
## Problem 1: Confirm prerequisites
## Solution
Confirm:
```
[ ] pet-shop-vpc exists
[ ] Public and private route tables are correct
[ ] pet-shop-db-subnet-group covers two Availability Zones
[ ] pet-shop-backend-sg exists
[ ] pet-shop-rds-sg allows 3306 only from pet-shop-backend-sg
[ ] pet-shop-backend-ec2-role exists
[ ] The USD 5 budget notifications exist
```
## Problem 2: Create RDS MySQL
## Solution
Use:
```
Creation method: Standard create
Engine: MySQL
Template: Free tier if eligible, otherwise Dev/Test
DB identifier: pet-shop-mysql
Initial database: pet_shop
Master username: pet_shop_admin
Deployment: Single-AZ
Instance class: Smallest suitable learning class
Storage: Smallest suitable General Purpose SSD allocation
Storage autoscaling: Optional with a conservative maximum
VPC: pet-shop-vpc
DB subnet group: pet-shop-db-subnet-group
Public access: No
Security group: pet-shop-rds-sg
Port: 3306
Backup retention: 1–7 days
Deletion protection: Enable when data becomes important
```
Review the current price estimate before creating the database.
Record securely:
```
RDS endpoint
Port
Database name
Master username
Master password
```
Do not store the password in Git, Java code, properties files, README files, Docker images, or React variables.
## Problem 3: Create the EC2 server
## Solution
Create:
```
Name: pet-shop-backend-ec2
Operating system: Ubuntu Server LTS
Instance type: Smallest suitable learning instance
VPC: pet-shop-vpc
Subnet: pet-shop-public-subnet-1
Public IPv4: Enabled
Security group: pet-shop-backend-sg
IAM role: pet-shop-backend-ec2-role
Storage: Small General Purpose SSD EBS volume
```
The Java runtime architecture must match the JAR build.
Use Systems Manager Session Manager for administration. Keep SSH only as a temporary restricted fallback.
## Problem 4: Install the runtime
## Solution
Install:
```
Java 21 runtime, if the project targets Java 21
Nginx
MySQL client
SSM Agent, if not already included
```
Confirm:
```
java -version
mysql --version
nginx -v
```
Do not install Maven or Gradle on the production server unless the chosen deployment process genuinely builds there. Prefer building a tested JAR before deployment.
## Problem 5: Test EC2-to-RDS connectivity
## Solution
From EC2:
```
mysql -h YOUR_RDS_ENDPOINT -P 3306 -u pet_shop_admin -p
```
Enter the password interactively, then run:
```
SHOW DATABASES;
USE pet_shop;
SHOW TABLES;
```
If it fails, check RDS status, endpoint, VPC, security groups, port, subnet group, and VPC DNS settings.
`Public access: No` is correct; EC2 reaches RDS over the private VPC network.
## Problem 6: Separate database users
## Solution
Create:
```
pet_shop_admin     → RDS administration only
pet_shop_migration → Flyway schema migrations
pet_shop_app       → Spring Boot application data access
```
Normal application permissions should normally be limited to:
```
SELECT
INSERT
UPDATE
DELETE
```
Grant the migration user schema-changing permissions only on `pet_shop.*`.
Do not use `pet_shop_admin` permanently in Spring Boot.
## Problem 7: Configure Spring Boot dependencies
## Solution
Recommended baseline:
```
Java 21 LTS
Spring Web
Spring Security, if authentication exists
Spring Data JPA
MySQL Connector/J
Flyway Core
Flyway MySQL support when required
Spring Boot Actuator
```
Use the existing project build tool. Do not change Maven to Gradle or Gradle to Maven without a project reason.
## Problem 8: Configure production settings
## Solution
Use environment variables for:
```
SPRING_PROFILES_ACTIVE=prod
DB_HOST
DB_PORT=3306
DB_NAME=pet_shop
DB_USERNAME=pet_shop_app
DB_PASSWORD
DB_MIGRATION_USERNAME=pet_shop_migration
DB_MIGRATION_PASSWORD
SERVER_ADDRESS=127.0.0.1
SERVER_PORT=8080
```
Recommended behavior:
```
spring:
  jpa:
    hibernate:
      ddl-auto: validate
    open-in-view: false
  flyway:
    enabled: true
server:
  address: 127.0.0.1
  port: 8080
management:
  endpoints:
    web:
      exposure:
        include: health,info
  endpoint:
    health:
      show-details: never
```
Do not use `ddl-auto: create` or `create-drop` in AWS.
Initial secret storage:
```
/etc/pet-shop/pet-shop.env
Owner-readable only
Not committed to Git
```
Next improvement:
```
Systems Manager Parameter Store SecureString
EC2 role restricted to the exact Pet Shop parameter path
```
Use Secrets Manager later when managed rotation is required.
## Problem 9: Manage schema with Flyway
## Solution
Store migrations under:
```
src/main/resources/db/migration
```
Rules:
```
Use unique increasing versions
Review SQL before deployment
Never modify an already-applied shared migration
Create a new migration for every later change
Create an RDS snapshot before risky production changes
```
Confirm `flyway_schema_history` and the expected Pet Shop tables exist after startup.
## Problem 10: Build and deploy a versioned JAR
## Solution
Deployment flow:
```
Run tests
    ↓
Build versioned JAR
    ↓
Review Flyway SQL
    ↓
Upload JAR to a versioned release location
    ↓
Update the active release
    ↓
Restart the service
    ↓
Check health
    ↓
Run smoke tests
```
Suggested locations:
```
/opt/pet-shop/releases/<version>/pet-shop-backend.jar
/opt/pet-shop/current → active release
/etc/pet-shop/pet-shop.env
```
Keep the previous working JAR for rollback.
## Problem 11: Run Spring Boot with systemd
## Solution
Create a dedicated non-login Linux user:
```
User: petshop
Not root
No interactive login
Minimum filesystem permissions
```
The systemd service must:
```
Run as petshop
Load /etc/pet-shop/pet-shop.env
Start java -jar from the active release
Wait for network-online.target
Restart on failure
Stop gracefully
Start automatically at boot
```
Check:
```
sudo systemctl status pet-shop-backend
sudo journalctl -u pet-shop-backend -f
curl http://127.0.0.1:8080/actuator/health
```
## Problem 12: Configure Nginx
## Solution
Nginx receives public traffic and proxies to:
```
http://127.0.0.1:8080
```
Forward:
```
Host
X-Real-IP
X-Forwarded-For
X-Forwarded-Proto
```
Test configuration before reload:
```
sudo nginx -t
```
After Nginx works, confirm there is no security-group rule for port 8080.
Do not expose sensitive Actuator endpoints such as `env`, `configprops`, `beans`, or `heapdump`.
## Problem 13: Configure HTTPS
## Solution
For the direct-EC2 learning architecture:
```
Create api.your-domain.example
Point it to the EC2 public address
Use Certbot/Let's Encrypt with Nginx
Redirect HTTP to HTTPS after certificate issuance
Test automatic renewal
```
ACM is the natural choice later when TLS terminates at CloudFront or an Application Load Balancer. A normal ACM certificate is not simply attached to standalone Nginx.
If there is no domain, use HTTP only for short testing and do not send real credentials or personal data.
## Problem 14: Host React with private S3 and CloudFront
## Solution
Create a globally unique frontend bucket:
```
Name pattern: pet-shop-frontend-<unique-suffix>
Block Public Access: Enabled
```
Create CloudFront:
```
Origin: Private S3 bucket
Origin access: Origin Access Control
Viewer protocol: Redirect HTTP to HTTPS
Default root object: index.html
Compression: Enabled
```
For React routing, configure an intentional `index.html` fallback without hiding real missing asset errors.
Deploy with caching rules:
```
Hashed JS/CSS/assets → long immutable cache
index.html → short or no cache
```
React configuration:
```
VITE_API_BASE_URL=https://api.your-domain.example/api/v1
```
Never place secrets in `VITE_*` variables because they are included in browser files.
## Problem 15: Configure CORS
## Solution
Allow only trusted origins:
```
Development: http://localhost:5173
Production: https://shop.your-domain.example
```
Do not use wildcard origins with credentials.
Allow only required methods and headers. Test preflight `OPTIONS` requests.
## Problem 16: Configure backups
## Solution
Use:
```
RDS automated backups: 1–7 days for learning
Manual snapshot: Before risky migrations
Deletion protection: Enable when data matters
```
Before calling the system production-ready, restore a snapshot into a temporary database and verify important data. Delete the temporary restored database afterward.
## Problem 17: Configure monitoring
## Solution
Monitor:
```
EC2: StatusCheckFailed, CPU, network, EBS health
Spring Boot: service state, startup failures, HTTP 5xx, DB failures
Nginx: access logs, error logs, 4xx and 5xx
RDS: CPU, connections, free storage, freeable memory, latency
```
EC2 does not publish guest memory and filesystem usage by default. Install the CloudWatch Agent when those metrics or centralized logs are required.
Set learning log retention to approximately:
```
7–14 days
```
Create only actionable alarms.
