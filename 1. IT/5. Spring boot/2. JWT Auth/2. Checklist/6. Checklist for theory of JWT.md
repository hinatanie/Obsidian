#### **Is JWT encrypted?**
`JWT` is usually `signed`, not `encrypted`.  
That means people can often `decode` and read the `header` and `payload`.  
Example JWT
```
<base64-encoded header>.<base64-encoded payload>.<base64-encoded signature>
```
`Base64 encode` is a way to convert raw data such as text, images or file into a text-safe format using a common set of 64 ASCII characters
Anyone can decode the middle part, the payload
```
{
  "userId": 10,
  "username": "nguyen",
  "role": "USER"
}
```
But they can not modify it without breaking the `signature`.

#### **What the header contains**
The `Header` contains metadata about the `token`
```
{
	"alg": "HS256",
	"typ": "JWT"
}
```
`typ` means `type`  
`alg` means `algorithm`
Common algorithms:

|Algorithm|Meaning|
|---|---|
|`HS256`|HMAC with SHA-256|
|`RS256`|RSA signature with SHA-256|
#### **What the payload contains**
The `Payload` contains the `actual data`

`Payload` contains `claims`

#### **What is signature used to**
The `Signature` is used to verify that the token has not been changed
#### **How is signature created**
The `signature` is created by signing the first two parts of the token
```
base64Url(header)+"."+base64Url(payload)
```
with a `secret key` or `private key`
Assume the `header` is
```
{
	"alg": "HS256",
	"typ": "JWT"
}
```
`JWT` first encodes the `header` and `payload` to
```
base64Url(header).base64Url(payload)
```
and then signs it using
```
signature =
HMAC-SHA256(
  base64Url(header) + "." + base64Url(payload),
  secret
)
```
#### **Why the information can be sent safely?**
The token has a `signature`  
The `signature` helps the backend check whether the `token` has been changed  
If someone changes the payload, for example:
```
{  "role": "ADMIN"}
```
the old signature will no longer match.
When the backend receives the token, it does this check again:
```
expectedSignature = sign(encodedHeader + "." + encodedPayload, secret)
```
Then it compares:
```
expectedSignature == tokenSignature
```
If they match, the token is valid.
If they do not match, the token was changed or signed with the wrong secret.
#### **What is secret key used to**
The `secret key` is only known by the backend  
the `secret key` is used to create and verify the `JWT signature`
#### **How many ways to sign JWT**
These are two ways to sign `JWTs`
```
HMAC is used to sign with secret key
RSA is used to sign with private key and public key
```
#### **What is HMAC**
`HMAC` is a way to create a secure `signature` from encoded header, payload using a secret key
`HMAC` uses `one secret key` used to
```
Create signature
Verify signature
```
#### **What does HMAC do**
`HMAC` checks whether the token is created by its server  
Because only your server knows the `secret key`
`HMAC` checks whether the token is changed
#### **What does HS256 have to do with HMAC**
`HS256` is the JWT algorithm name for **HMAC-SHA256**.
#### **What is RSA**
`RSA` is a cryptographic algorithm that uses `two keys`  
`Private key` is kept secret on the server and used to create JWT signature  
`Public key` can be shared and used to verify JWT signature but it cannot create a valid signature
In JWT, you may see algorithms like:
```
{  "alg": "RS256",  "typ": "JWT"}
```
The JWT signature is created like this:
```
signature = 
RSA-SHA256(
  base64Url(header) + "." + base64Url(payload),
  privateKey
)
```
Then when the backend or another services receives the token, it verifies signature using `publicKey`
This is useful when one service creates tokens and other services only need to verify them  
Example:
```
Auth Service creates JWT using private key
User Service verifies JWT using public key
Payment Service verifies JWT using public key
Order Service verifies JWT using public key
```
Only the Auth Service has the **private key**, so only it can create valid tokens.  
Other services only need the **public key**, so they can verify tokens safely.
#### **What is the problem with HMAC**
Because the same secret can create and verify tokens, every service that can verify tokens also has the power to create tokens  
Example for
```
Auth Service
Profile Service
Post Service
Post Service
Payment Service
```
`RSA` uses two different keys
```
Private key
Public key
```
The `private key` is secret  
and only `Auth Service` should have it  
It is used to create JWT signature
The `public key` is not secret  
Other services can have it  
It is used to verify JWT signature
So `RSA` means
```
Private key signs
Public key verifies
```
#### **What does RS256 have to do with RSA**
`RS256` is the JWT algorithm name for **RSA-SHA256**.
