Learn **Database per Service** by first understanding the problem it solves.
### Main idea
In a microservice system, each service should **own its own data**.
```text
+-------------------+
| User Service      |
|                   |
| users database    |
+-------------------+
+-------------------+
| Trip Service      |
|                   |
| trips database    |
+-------------------+
+-------------------+
| Payment Service   |
|                   |
| payments database |
+-------------------+
```
The important rule is:
```text
Trip Service should NOT directly query User Service's tables.
```
So avoid this:
```text
Trip Service
    |
    | SELECT * FROM users
    v
User Database
```
Prefer this:
```text
Trip Service
    |
    | GET /users/123
    v
User Service
    |
    v
User Database
```
Why? Because if `Trip Service` freely touches `users` tables, it becomes tightly coupled to the internal database design of `User Service`.
For example, today User Service has:
```sql
users
- id
- name
- phone
```
Tomorrow the User team changes it to:
```sql
users
- id
- full_name
user_phones
- user_id
- phone
```
If Trip Service directly queries those tables:
```text
User Service changes database
            ↓
Trip Service breaks
```
But if Trip Service only calls:
```http
GET /users/123
```
User Service can change its database however it wants, while keeping the API response stable.

---
For your **RideNow** project, practice with only 2 services first:
```text
+-----------------------+
| User Service          |
|                       |
| DB: user_db           |
|                       |
| users                 |
+-----------------------+
+-----------------------+
| Trip Service          |
|                       |
| DB: trip_db           |
|                       |
| trips                 |
+-----------------------+
```
Create these databases:
```text
user_db
└── users
trip_db
└── trips
```
Then make `Trip` contain only something like:
```text
trips
id
passenger_id
driver_id
status
pickup_location
destination
```
Notice:
```text
passenger_id
```
exists in `trip_db`, but the actual passenger record belongs to `user_db`.
Don't do a database join like:
```sql
SELECT *
FROM trips
JOIN user_db.users
ON trips.passenger_id = users.id;
```
Instead:
```text
1. Trip Service reads trip
2. passenger_id = 123
3. Trip Service calls User Service
   GET /users/123
4. User Service returns passenger information
```
Your learning exercise should be this:
```text
Exercise 1
User Service owns users.
Exercise 2
Trip Service owns trips.
Exercise 3
Create trip using passengerId.
Exercise 4
Try to display:
trip + passenger information.
Do NOT use cross-database JOIN.
Use REST between services.
```
Then intentionally change the User database schema and see whether Trip Service breaks. If Trip Service only depends on the User API, it shouldn't care about the internal schema change.
After that, learn the harder problem:
```text
What if Trip Service needs user data constantly?
What if User Service is down?
What if I need one query containing data
from 5 different services?
```
Those questions lead naturally into **data duplication, eventual consistency, events, CQRS, and API composition**.
For now, remember one rule:
> **A service owns its data. Other services ask the owner instead of directly manipulating its tables.**
