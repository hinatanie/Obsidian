```text

| Trip Service     | ----------------------> | User Service     |
|                  |   GET /users/{id}       |                  |
+------------------+                         +------------------+
```
For your **RideNow** project, imagine `Trip Service` needs passenger information from `User Service`.

To master Service-to-Service communication via REST, you need to shift your mindset from _local function calls_ (inside a monolith) to _network requests_ (across microservices).
Here is a step-by-step framework to learn and implement this practically using your RideNow project:

---
## Step 1: Simulate the Split (Conceptually)
Before writing complex network code, imagine you have split your RideNow monolith into two separate applications running on different ports on your local machine:
- Trip Service running on `http://localhost:8081`
- Passenger Service running on `http://localhost:8082`
When a user requests a ride, the Trip Service receives the request. However, it only gets a `passenger_id`. It does not know the passenger's name, phone number, or rating. It needs to ask the Passenger Service for this information over the network.

---
## Step 2: Implement a Synchronous HTTP Client
To make a service talk to another service, you must use an HTTP Client library inside your code. This replaces traditional database joins.
Depending on your tech stack, you should learn how to use these native HTTP clients to make a `GET` request from one service to another:
- Node.js / JavaScript: `axios` or native `fetch`
- Java / Spring Boot: `WebClient` or `RestTemplate`
- Python: `requests` or `httpx`
- Go: Native `net/http` package
Your Coding Exercise: Write a function inside the Trip Service that triggers an HTTP `GET` request to `http://localhost:8082/passengers/{passenger_id}`, parses the returning JSON, and logs the passenger's profile.

---
## Step 3: Handle Network Failures (The Crucial Step)
In a monolith, calling a function either works or throws a code error. In microservices, the network can fail randomly. You must learn to handle these 3 scenarios in your code:
1. The Target Service is Dead: What happens to the Trip Service if the Passenger Service crashes entirely? (Learn to handle connection timeouts).
2. The Target Service is Slow: What if the Passenger Service takes 10 seconds to respond? It will clog your Trip Service memory. (Learn to set strict request timeouts, e.g., max 2 seconds).
3. The Target Service returns an Error: Learn to correctly map downstream HTTP status codes (like `404 Not Found` or `500 Internal Server Error`) so your main service doesn't crash.

---
## Step 4: Protect Your Services (Resilience Patterns)
Once your basic HTTP calls work, you must learn how to make them resilient using standard libraries (like _Resilience4j_ for Java, or _Polly_ for .NET):
- Retry Pattern: If a request fails due to a temporary network glitch, automatically try again 1 or 2 times before giving up.
- Circuit Breaker Pattern: If the Passenger Service fails 10 times in a row, the Circuit Breaker "trips." The Trip Service stops sending requests over the network entirely for a few minutes and immediately returns a fallback response (e.g., "Passenger info temporarily unavailable") to save system resources.

---
## Step 5: Understand the Pitfalls (Why we eventually need Kafka)
As you build this, you will naturally hit the limits of REST for service-to-service communication. You will experience:
- Tight Coupling: If the Passenger Service goes down, the Trip Service cannot complete a ride request.
- Performance Bottlenecks: If Service A calls Service B, which calls Service C, the user has to wait for all three network hops to finish. This is called a distributed dependency chain.
Experiencing these pain points firsthand is _exactly_ how you prepare yourself for Step 5: Async communication (Kafka/RabbitMQ).
