I’d give you **6 projects**, ordered from easier to harder. Each one trains exactly the skills used in that workshop.
1. **AWS Read-Only Security Reviewer**  
    Build a small tool that inspects an AWS account and produces a risk report. Use Python or Java, AWS SDK, and a read-only IAM role. Check things like public EC2, open Security Groups, public S3 buckets, public RDS, and overly broad IAM permissions. Output: `environment-map.md`, `risk-report.md`, and an evidence table with resource ID, finding, source, and severity.
2. **Agent With Safe Cloud Tools**  
    Build an AI Agent that can answer questions about AWS, but only through safe read-only tools such as `list_ec2`, `describe_security_groups`, `list_s3_buckets`, and `get_cloudwatch_metrics`. The important part is not the chatbot—it is the permission boundary. Add a forbidden tool such as `terminate_ec2` and prove that the Agent cannot execute it. Output: architecture diagram, allowed-tools list, denied-actions test, and audit log.
3. **Broken Cloud Environment Investigation**  
    Create a deliberately broken application. Example:
```text
Internet
   |
   v
ALB
   |
   v
EC2 / App
   |
   v
RDS
```
Introduce one fault, such as:
- Security Group blocks DB traffic
- wrong DB password
- DB connection pool exhausted
- CPU overload
- unhealthy ALB target
- application crashes after deployment
Then pretend you do not know the answer. Investigate using logs and metrics. Create at least 3 hypotheses before concluding anything. Output: `incident-report.md`, timeline, Evidence Table, competing hypotheses, and root cause.
4. **Cloud Incident Detective Game**  
    This one is especially good for you. Write a script that randomly creates one of several incidents in Docker or AWS. Example incidents: Redis unavailable, database stopped, wrong environment variable, port closed, high CPU, disk full, dependency timeout. Your job is to diagnose it without looking at the code that injected the failure.
Use a fixed investigation template:
```text
Signal
↓
Hypothesis A
Hypothesis B
Hypothesis C
↓
Evidence collection
↓
Reject / support hypotheses
↓
Root cause
```
This forces you to practice investigation instead of memorization.
5. **Evidence-First Incident Agent**  
    Build an Agent that is not allowed to answer immediately. When asked:
> Why is the API failing?
it must first collect evidence.
For example:
```text
User
 |
 v
Agent
 |
 +--> CloudWatch metrics
 |
 +--> Application logs
 |
 +--> EC2 state
 |
 +--> Security Groups
 |
 v
Evidence Table
 |
 v
Hypotheses
 |
 v
Conclusion
```
Make the Agent return:
```text
Conclusion:
Database connection exhaustion
Confidence:
High
Evidence:
E1...
E2...
E3...
Rejected hypotheses:
H1...
H2...
Missing evidence:
...
```
This project is very close to the workshop idea.
6. **Mini Prove It Arena**  
    This should be your final project. Give yourself **85 minutes** and use an environment you have never inspected before. Better: ask a friend to modify your Docker/AWS environment secretly.
Your tasks are:
- draw the Environment Map
- identify the top 5 risks
- detect the incident
- create 3+ hypotheses
- collect timestamped evidence
- create a causal graph
- determine root cause
- propose remediation
- write an Investigation Dossier
- defend the conclusion verbally in 5 minutes
Score yourself with the same structure from the workshop:

|Area|Points|
|---|--:|
|Agent governance|15|
|Environment review|20|
|Incident investigation|30|
|Remediation|20|
|Evidence defence|15|
For you, I recommend starting with **Project 1**, then doing **3 → 5 → 6**. That path gives you the highest practical value without spending too much time building AI plumbing first.
A very good overall progression is:
```text
Project 1
AWS Security Reviewer
        ↓
Project 3
Manual Incident Investigation
        ↓
Project 5
AI-assisted Investigation
        ↓
Project 6
Full Prove It Arena
```
The key rule for every project should be:
```text
NO CLAIM WITHOUT EVIDENCE
```
So instead of:
```text
RDS caused the outage.
```
you must produce:
```text
E1: RDS connections reached 100% at 10:04
E2: API 5xx increased at 10:05
E3: application logs show DB timeout at 10:05
Therefore:
RDS connection exhaustion is the most supported hypothesis.
```
