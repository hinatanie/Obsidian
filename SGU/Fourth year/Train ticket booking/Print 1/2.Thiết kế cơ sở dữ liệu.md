This database structure is for an **airline booking system**. 
### 1. `users`
Stores information about people who use the system.
Typical fields:
```text
id
full_name
email
password_hash
phone
role_id
created_at
```
Example users:
- Customer
- Admin
- Airline staff
The relationship between users and roles is:
```text
roles 1 ---- N users
```
One role can belong to many users.
### 2. `roles`
Stores the permissions or type of user.
Example data:
```text
ADMIN
CUSTOMER
STAFF
```
Instead of storing `"ADMIN"` directly inside every user record, `users` can reference `roles`.
For example:
```text
roles
id = 1
name = ADMIN
users
id = 100
name = John
role_id = 1
```
So John has the `ADMIN` role.
### 3. `airports`
Stores airport information.
Typical fields:
```text
id
code
name
city
country
```
Example:
```text
id
SGN
Tan Son Nhat International Airport
Ho Chi Minh City
Vietnam
```
A flight usually references two airports:
```text
departure_airport_id
arrival_airport_id
```
For example:
```text
SGN -> HAN
```
means a flight from Ho Chi Minh City to Hanoi.
### 4. `aircrafts`
Stores aircraft information.
Typical fields:
```text
id
model
manufacturer
registration_number
capacity
```
Example:
```text
id
Aircraft:
VN-A123
Airbus A321
Capacity: 200
```
This table represents the **physical aircraft** used by the airline.
### 5. `aircraft_seats`
Stores the seat layout of an aircraft.
For example:
```text
1A
1B
1C
2A
2B
2C
...
```
Typical fields:
```text
id
aircraft_id
seat_number
seat_class
```
Relationship:
```text
aircrafts 1 ---- N aircraft_seats
```
`aircraft_seats` describes the **physical seat configuration**.

---
### 6. `flights`
Stores the general flight definition.
For example:
```text
VN210
Ho Chi Minh City -> Hanoi
```
Typical fields:
```text
id
flight_number
departure_airport_id
arrival_airport_id
```
You can think of `flights` as the **route / flight identity**, not necessarily a specific flight on a particular day.
For example:
```text
VN210
SGN -> HAN
```
may operate every day.
### 7. `flight_schedules`
Stores a specific occurrence of a flight.
This distinction is very important.
`flights`:
```text
VN210
SGN -> HAN
```
`flight_schedules`:
```text
VN210
September 14
08:00 -> 10:00
VN210
September 15
08:00 -> 10:00
VN210
September 16
08:00 -> 10:00
```
Typical fields:
```text
id
flight_id
aircraft_id
departure_time
arrival_time
status
```
Relationship:
```text
flights 1 ---- N flight_schedules
```
One flight can have many scheduled departures.
### 8. `flight_seats`
Stores the seats that are available for a **specific scheduled flight**.
This is different from `aircraft_seats`.
`aircraft_seats` says:
```text
Aircraft VN-A123 has seat 12A.
```
`flight_seats` says:
```text
Seat 12A on flight VN210
on September 14
is AVAILABLE.
```
Typical fields:
```text
id
flight_schedule_id
aircraft_seat_id
price
status
```
Example:
```text
Flight VN210 - Sep 14
12A -> AVAILABLE
12B -> BOOKED
12C -> AVAILABLE
```
This table is very important because the **same physical seat can have different booking states on different flights**.
### 9. `bookings`
Stores a customer's booking/order.
Example:
```text
Booking BK001
Customer: John
Flight: VN210
Status: CONFIRMED
Total: $150
```
Typical fields:
```text
id
booking_code
user_id
flight_schedule_id
status
total_amount
created_at
```
Relationship:
```text
users 1 ---- N bookings
```
One user can make many bookings.

---
### 10. `booking_passengers`
Stores the passengers included in a booking.
This is necessary because the person who creates the booking is not always the passenger.
For example, John creates one booking for:
```text
John
Mary
Peter
```
Then:
```text
bookings
BK001
booking_passengers
John
Mary
Peter
```
Typical fields:
```text
id
booking_id
full_name
date_of_birth
gender
passport_number
```
Relationship:
```text
bookings 1 ---- N booking_passengers
```
One booking can contain multiple passengers.

---
### 11. `tickets`
Represents the actual ticket issued to a passenger.
A passenger normally receives a ticket after the booking is confirmed.
Typical fields:
```text
id
ticket_number
booking_passenger_id
flight_seat_id
status
issued_at
```
For example:
```text
Ticket: T001
Passenger: Mary
Flight: VN210
Seat: 12A
```
A useful way to think about it is:
```text
Booking = the order
Passenger = the person travelling
Ticket = that passenger's right to travel on the flight
```
If a booking has 3 passengers, it can produce 3 tickets.

---
### 12. `payments`
Stores payment transactions for bookings.
Typical fields:
```text
id
booking_id
amount
payment_method
status
transaction_id
paid_at
```
Example:
```text
Booking BK001
Amount: $150
Method: CREDIT_CARD
Status: SUCCESS
```
Possible statuses:
```text
PENDING
SUCCESS
FAILED
REFUNDED
```
You may allow several payment attempts for one booking.
For example:
```text
Booking BK001
Payment 1 -> FAILED
Payment 2 -> FAILED
Payment 3 -> SUCCESS
```
So a common relationship is:
```text
bookings 1 ---- N payments
```

---
The overall business flow is roughly:
```text
User
  |
  v
Search Flight
  |
  v
Flight
  |
  v
Flight Schedule
  |
  v
Choose Flight Seat
  |
  v
Create Booking
  |
  v
Add Passenger(s)
  |
  v
Payment
  |
  v
Issue Ticket(s)
```
The most important distinction to understand is this:
```text
aircraft
    = physical airplane
aircraft_seat
    = physical seat inside that airplane
flight
    = flight definition / route, e.g. VN210 SGN -> HAN
flight_schedule
    = VN210 departing at a particular date and time
flight_seat
    = seat availability for that particular scheduled flight
booking
    = customer's order
booking_passenger
    = person travelling
ticket
    = travel document issued to one passenger
payment
    = money transaction for the booking
```
If you understand these distinctions, the rest of the database design becomes much easier.
